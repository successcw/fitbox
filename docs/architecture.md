# 架构与数据说明

总览图和物理连接图见 [README](../README.md)，安装步骤见 [部署说明](deployment.md)。

## 职责划分

| 位置 | 模块 | 责任 |
|---|---|---|
| 树莓派 | `cpap_pull.py`、`cpap_legacy.py` | 切换到卡热点，读取 EDF，验证并写入采集索引，恢复家庭网络 |
| 树莓派 | `scale_daemon.py` | 监听受支持体脂秤，记录称重结果 |
| 树莓派 | `health_receiver.py` | 校验请求 Token，原样保存 Health Auto Export JSON，追加事件索引 |
| 树莓派 | systemd timer、网络恢复脚本 | 定时采集、成功后跳过、掉线后的网络恢复 |
| Mac | `watch.py`、`pull.py` | 主动通过 SSH 追踪索引，经 SCP 拉取文件，校验后落盘与去重 |
| Mac | `health_daily.py` | 合并汇总指标，选择报告日期，管理发送与补发状态 |
| Mac | `sleep_analysis.py`、`sleep_waveform.py`、`sleep_stages.py` | 解析治疗时段、波形与事件，按手表阶段进行时间对齐 |
| Mac | `health_card.py`、`notify.py` | 生成日报，通过 Telegram 发送 |

树莓派无需主动连接 Mac。Mac 恢复联网时重放事件索引，已有完整文件跳过，失败文件重试。不要把事件索引当作只读一次后即可清空的消息队列。

## 呼吸机采集过程

1. 定时任务检查当天的成功状态；已完成则退出。
2. 建立独立网络恢复任务，再连接 ezShare 热点。
3. 获取 `STR.EDF`，定位目标治疗日与治疗起止时间。
4. 根据目标治疗日和已验证的命名规则定位 `DATALOG` 文件；旧固件可通过直接路径读取。
5. 校验 EDF 头、记录长度与文件大小，临时文件写完后原子替换，记录 SHA-256 和字节数。
6. 恢复家庭网络，Mac 随后继续同步。独立恢复机制为采集异常退出提供保障。

呼吸机治疗日通常采用中午到次日中午的边界，不能把 `DATALOG` 目录名直接当作醒来日期。文件名、EDF 头部时间和治疗日需要一致验证。

旧卡可能对不存在的路径返回 HTTP 200 和欢迎页；HTTP 成功不代表得到 EDF。配套 CRC 文件也不等于本项目实现了厂商 CRC 算法，完整性检查应按实现区分。

## 网络与硬件边界

ezShare 是呼吸机内的 SD 卡，同时提供 Wi-Fi 热点。树莓派从热点读取文件，不模拟呼吸机，不通过 USB 访问 SD，也不修改治疗设置。

单 Wi-Fi 网卡不能同时保持家庭 Wi-Fi 和卡热点连接。访问卡时的 Tailscale 暂断是网络拓扑的结果，程序需要恢复家庭网络，而不是无限重试远程 SSH。以太网可以提供独立网络出口；部署时仍应确认网络优先级、卡子网路由及恢复策略。

Health Auto Export 的接收服务通过 Tailscale 私有网络使用，Token 是应用层校验。限制访问接口与端口属于部署责任，不能仅因为配置了 Token 就把接收服务暴露到公网。

## 手表汇总与逐段数据

实际部署有健康汇总（过去 7 天）、睡眠明细（今天全部健康指标）和锻炼（过去 7 天）三路。日报取昨天健康汇总、今天睡眠与恢复采样、昨天锻炼；日汇总优先，局部明细不覆盖它：

| 输入 | 典型内容 | 用途 |
|---|---|---|
| 每日汇总 | `sleepStart`、`sleepEnd`、`totalSleep`、`deep`、`rem`、`core`、`awake` | 日报总量、整晚窗口、趋势 |
| 逐段明细 | `startDate` / `start`、`endDate` / `end`、`value` | 生成睡眠日统计、时间轴与分阶段统计；数值明细按时间戳去重后按日聚合 |

重复导出的同一阶段区间先合并；不同阶段相互重叠时停止该晚分期统计并标记问题。无阶段标签的整晚窗口不能用于伪造分期时间轴。

Mac、树莓派、手机和呼吸机时钟都应核对。时区配置必须与设备实际含义一致，尤其需要留意 EDF 中没有明确时区的本地时间。改变配置不能自动纠正呼吸机时钟本身的误差。

## 分阶段统计如何计算

统计只使用手表阶段、呼吸机治疗时段和有效波形三者的重叠部分：

1. 加载手表阶段区间并去重，裁剪到整晚睡眠窗口。
2. 与呼吸机有效治疗时段取交集。
3. 从 PLD EDF 获取呼吸频率与漏气，验证单位；漏气由 L/s 转为 L/min。
4. 每个采样值按实际覆盖秒数加权，计算呼吸频率中位数与漏气 P95。
5. 展示匹配时长和阶段总时长。匹配不足 80% 或有效匹配不足 5 分钟时，该阶段指标显示“—”。

系统还检查整晚分期覆盖率与数据问题，决定是否视为完整明细。短暂清醒时段可能达不到展示门槛，不应为得到一个数字而降低门槛。

**合成解释例子**：若深睡漏气 P95 为 8 L/min，快速眼动为 12 L/min，只表示各自有效重叠时段内，95% 的时间漏气分别不超过这些值。它不等于平均漏气相差 4 L/min，也不能据此推断面罩漏气造成了某种睡眠阶段。

## 指标的依据与限制

- AHI 以 `<5` 作为日报中的治疗目标参考。
- 漏气 P95 使用 24 L/min 作参考线；瑞思迈 AirView 的完整规则还涉及连续多日条件，本项目的单晚指示没有复现整套规则。
- 呼吸频率按个人已有多晚历史范围提示变化，不宣称某一阶段存在统一的瑞思迈“正常区间”。
- 分阶段对照、使用覆盖率与单晚趋势是本项目统计；手表阶段不是多导睡眠监测结果，相关性也不是因果结论。

具体来源保存在 [睡眠分析参考](sleep-analysis.md)。这些统计用于回顾数据，不自动调整治疗参数。

## 可靠性与运行依赖

- 下载与跨设备拷贝使用临时文件，完整校验通过后才替换正式文件。
- EDF 验证、事件索引与报告状态分别负责文件完整性、同步重试和发送去重。
- 日报以健康汇总提供昨日指标、睡眠明细提供今日睡眠、锻炼导出提供昨日项目；分期图额外需要完整波形。缺少时应保留明确缺失状态。
- Mac 休眠或离线会延迟出报；树莓派上的独立采集不因此停止。
- 手机自动化可能延迟，呼吸机也可能直到治疗结束才完成文件写入，所以定时采集包含补漏档。

## 公开版与运行版

公开版保留通用实现、部署模板、测试、协议经验和合成演示。运行版的健康档案、真实网络配置、设备标识和发送凭据不属于源码发布内容。两份目录独立，更新公开版不会自动部署到现有 Mac 或树莓派；真实部署必须按目标环境重新配置、验证。
